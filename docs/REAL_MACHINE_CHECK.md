# 実機確認の手順（HC20 / YRC1000）— 読むだけの確認

この手順は、会社のPCで実機のジョブを確かめるときに使います。
**今の段階では、アプリはジョブを書き出しません。実機は動かしません。** 確認は「読む・見る」だけです。
アプリの検査を通ったことは、物理的な安全の保証ではありません。実機を動かすこと・ジョブを書き込むことは、別途の安全確認と唐川さんの明示的な承認のあとで行います。

## 今回確かめたいこと
1. 実際のJBIを解析できるか（「読めません」や「確認できない点」が出ないか）
2. C00000 などの位置番号と値が正しく表示されるか
3. ROBOT / PULSE の判定が正しいか
4. PL・CR などの命令が正しく認識されるか
5. 解析できない行を、正しく「確認できない点」として報告できるか

## 今夜できること・できないこと
| できる | できない（作っていない、またはレビュー前） |
|---|---|
| 実機のジョブを読み、形式・位置・命令を一覧と2Dの図（X・Y、X・Z、Y・Z）で見る | ジョブの書き出し・USBへの出力・転送・実機の起動 |
| 位置ごとに、このアプリの**形式の検査**で通るか、止まる理由は何かを見る（専門家の枠の検査はまだ無いので、「通る」は変更の許可ではない） | 音声入力、Claudeによる解釈、承認画面、3D表示 |

## 0. 実機のデータを外に出さないための約束（最初に読む）
- 実機のジョブ（.JBI）と、このツールが作る HTML は、**リポジトリの外**（例：`C:\vt_private\`）にだけ置く。`samples/dummy/` には絶対に置かない（`.gitignore` がそこだけは許可しているため、コミットできてしまう）
- コマンドは**普通のターミナル**（PowerShell・コマンドプロンプト）で実行する。Claude Code や、AI補助が有効なエディタのターミナルでは実行しない（画面の文字が AI に送られるため）
- JBI と HTML を、AI補助が有効なエディタで開かない。HTML は Chrome で開く
- 画面の写真・スクリーンショット・ジョブの中身を、Claude にも ChatGPT（チャッピー）にも貼らない。伝えるのは下のチェック表の「形式・書き方」の結果だけ
- 終わったら、リポジトリのフォルダで `git status` を実行し、何も変わっていない（空）ことを確かめる

## 1. 準備（会社のPC）
1. このブランチが GitHub に push 済みであることを確かめる（レビューが終わるまでは push されないので、その場合は今夜の確認はできない）
2. `git fetch` → `git checkout fix/safety-guards` → `git pull`
3. 必要なもの：Python 3.10 以上。このツールは標準ライブラリだけで動く（`pip install` は不要）。テストを実行するには pytest が要る（`pip install -r requirements.txt`）。社内ネットワークで pip が使えないときは、テストは飛ばして 2. へ進み、その旨を記録する
4. （pytest がある場合）`python -m pytest -q` を実行し、すべて通ることを確かめる。通らなければここで止めて、出たメッセージ（ジョブの中身を含まないもの）をクロに伝える

## 2. ジョブを USB で PC へ写す（ペンダントの操作）
- ペンダントの外部メモリの操作では、**「セーブ」（ロボット → USB）だけを使う。「ロード」（USB → ロボット）はしない**。コントローラのジョブを上書きしないため
- 写したら、USB からリポジトリの外のフォルダ（例：`C:\vt_private\`）へコピーする

## 3. ジョブを読む（読むだけ）
```
python -m voice_teaching.inspect_job C:\vt_private\ジョブ名.JBI --out C:\vt_private\out
```
- ジョブは書き換えません。JBI は書き出しません。出すのは HTML だけです
- 画面には件数だけを出します（位置の値は出しません）。位置の一覧と図は、HTML を Chrome で開いて見ます
- 「読めません」と出たときは、そのメッセージの種類（文字コード・形式など）だけを記録する（ジョブの中身は書き写さない）

## 4. 人が確かめること（チェック表）
クロに伝えるのは「形式」と「書き方」だけにする（実機の数値・コメント・ジョブの中身は送らない）。

| # | 確かめること | 見る場所 | 結果 |
|---|---|---|---|
| 1 | 位置の保存形式（`///POSTYPE` が ROBOT か PULSE か。`///RECTAN` があるか）**最重要**。PULSE なら図は描かれない（無理に変換しない） | HTML の「位置」の「形式」 | |
| 2 | 表示された C00001 などの値が、ペンダントの位置表示と合っているか（2〜3点）。**同じ座標系（ロボット座標）と、同じツール番号（`///TOOL`）で比べる**。ペンダントで位置の内容を表示して確かめるだけにし、確かめるためにロボットを点まで動かすかどうかは唐川さんが決める（動かす場合は、普段の教示のときの安全の手順に従う） | HTML の「ファイルの行」とペンダント | |
| 3 | ツール番号（`///TOOL`）、`///RCONF`（形態）、`///USER` の書き方。位置の値の個数（6個か） | HTML の「形式」「ファイルの行」 | |
| 4 | MOVL に `PL=` が書かれているか。**PL=0 が `PL=0` と書かれるのか、何も書かれないのか**（必ず記録する） | HTML の「文字での一覧」の移動命令 | |
| 5 | `CR=`、MOVJ・MOVC など MOVL 以外の命令の有無 | 同上 | |
| 6 | `V=` の単位（ペンダントの表示単位の設定） | ペンダント | |
| 7 | 「確認できない点」に出た行の**種類**（例：`///LVARS` の形、知らない命令の名前、`//ALIAS` などの見出し） | HTML の「確認できない点」 | |
| 8 | 文字コードと改行（Shift_JIS か、CRLF か） | HTML の先頭 | |
| 9 | 図の上下左右の向きが、実機の向きと合っているか（「右」がX・Yのどちらで、＋か−か） | 図とロボット | |
| 10 | 同じ位置を2つ以上の命令が使っていないか（「共用」と出ていないか） | HTML の「使っている行」 | |

### 結果の見方（分かれ道①：位置と速度のどちらを柱にするか）
- **#1 が PULSE** → 位置（XYZ）を直す前提が崩れる。仕様 v2.1 の分かれ道に従い、速度を柱にする案を唐川さんが判断する
- **#4 で `PL=0` と明示されている** → 現在の実装は正本に合わせて PL=0 を通すよう修正中。修正の前のコードでは「断る」と表示されるので、PULSE（形式が合わない）とは区別して記録する
- **#7 に多数出る** → 許可リストが実機の書き方に足りていない。種類を伝えてもらえれば、テストを足してから許可するかどうかを相談する

## 5. 将来、アプリで直したジョブを実機で動かす前に（今夜は対象外）
書き出しが作られ、QA・Safety のレビューと唐川さんの承認を通ってから行う。仕様 v2.1 の6章「撮影前の確認手順」に沿って、次を人が確かめる。
1. 生成したジョブの差分：変わったのは承認した1行だけか（位置の値、または速度の値）。ジョブ名が新しい名前になっているか。元のジョブが残っているか
2. 座標系：変えた位置がロボット座標で、ツール番号・姿勢（Rx・Ry・Rz）・形態（RCONF）が変わっていないか
3. 速度：変えた `V=` の値と単位
4. 動作範囲：動かした点に出入りする区間も横にずれる。動かす向きの空き、周りの物の配置
5. 最初は、カメラの外で低速・ステップで確認する
6. 動作範囲に人がいない（協働ロボットでも）。非常停止の位置を確認する
7. ジョブはペンダントで人が選び、スタートボタンで動かす（アプリからは起動しない）
