## 1. 目的と範囲

### 目的
「自然な言葉で使いやすく、曖昧な操作は確実に止まるアプリ」にする。言い方の小さな揺れで止まらないようにし、曖昧なものはこれまでどおり止める・聞き返す。

### やること
- 案1：方向の言い方の単純な揺れ（「Y-の方向に」など）を、**プログラムの読み取りの形を広げて**読めるようにする（案1-a）。プログラムで読めなかったときだけ使う Claude の補助（案1-b）の設計。補助は既定で使わない
- 案2：右・左・手前・奥（・前・後ろ）を、**設備ごとに専門家が登録して照合に通ったときだけ**軸に当てる。登録が無いときは6択（X+〜Z−）を、基準座標系・対象位置・移動方向・移動量と一緒に見せる
- 案4：ヘッダー左上のロゴを押すとホームに戻る。戻ると失われる作業があれば確認する。戻ったあと前の候補を承認・出力できないことをサーバー側でも保証する

### やらないこと
- 承認・出力の決まりの変更（承認はボタンだけ、承認していないものは出力しない、は今のまま）
- 20mm の上限・累積の上限・MOVL 以外・PL>0 などの検査の変更
- Claude にジョブの文字列・数字・軸・符号を作らせること
- 画面の 3D の向き（カメラの向き）から右・左を決めること
- 音声・Claude・画面のボタンから方向の登録を書くこと
- ロボットへの転送・起動
- 速度の変更（今は止めている。変えない）

## 2. 案1：言い方の揺れ

### 2-1. 方針（チャッピーの条件）
1. 単純な揺れは、まずプログラムの読み取り（`read_utterance`）で読む。Claude は使わない（案1-a）
2. Claude は、プログラムで読めなかったときだけの補助（案1-b）。補助は既定で使わない（設定で入れる。入れるかは唐川さんが決める：Q1-3）
3. 初期の方向語（符号の言葉）は「+」「-」「プラス」「マイナス」だけ。今の `normalize`（NFKC、`−‐‑–` → `-`）と `_spoken`（PLUS・MINUS → プラス・マイナス、ワイ → Y など）で揃えた後の4つ。「正」「負」「ー（長音）」「側」「向き」「方」は方向語として足さない

### 2-2. 案1-a：プログラムで読めるようにする言い方

新しい読み方の形を1つ足す（考え方の例。実装のときに受入テストで固める）：

```
_AXIS_SIGN_DIR = r"(?<![A-Z])([XYZ])\s?(?:軸\s?)?(?:の\s?)?(マイナス|プラス|[+\-])\s?(?:の\s?)?(?:軸方向|方向)"
```

- 必ず「軸の文字 → 符号 → 方向」の順で、間に入ってよいのは「軸」「の」（各1回まで）と空白だけ
- 符号は軸に付けて読む（`axis_signs` に入れ、`placed_axis_signs` に数える。`stray_signs` にしない）
- 読んだ範囲は全部「使った」として取り除く（`used_patterns` と、知らない言葉を調べる前の取り除きに入れる）。字の数は変えない（今の作りどおり、空白にするだけ）
- 今の `_AXIS_RE` で読んでいた「Y-方向」と同じ所を2回数えない（読んだ範囲が重なったら1つとして数える）

| 足す言い方 | 例 | 読めるようになる理由 |
|---|---|---|
| 軸 符号 の 方向 | Y-の方向に10mm／Yマイナスの方向に10mm／Y+の方向に／Yプラスの方向に | 符号と「方向」の間の「の」を受け付ける |
| 軸 の 符号 方向 | Yのマイナス方向に10mm／Yの-方向に10mm | 軸と符号の間の「の」を受け付ける（今は「どこに付くか分かりません」） |
| 軸 の 符号 の 方向 | Yのマイナスの方向に10mm／Yの-の方向に10mm | 上の2つを両方 |
| 軸 軸 符号 （の）方向 | Y軸マイナス方向に／Y軸のマイナス方向に／Y軸の-方向に | 「Y軸」の後の符号 |
| 空白の入った形 | Y - の 方向 に 10 mm | 音声認識が空白を入れる（`\s?`） |
| 全角・音声の書き方 | Ｙ－の方向に１０ｍｍ／ワイマイナスの方向に10ミリ／Y MINUS の方向に 10 mm | 今の `normalize`・`_spoken` のあとに同じ形になる |
| 量が先 | 10mm Y-の方向に | 今の読み方は並びに依らず量を読む。同じ節（区切りの無い1つの文）の中だけ |

読めるようにしない（今どおり聞き返す・止める）もの：

| 言い方 | 扱い | 理由 |
|---|---|---|
| Yの方向に10mm（符号なし） | 聞き返し（プラスかマイナスか） | 符号を補わない |
| マイナスYの方向に10mm（符号が先） | 聞き返し（符号の付く所が分からない） | 符号が軸の前にある形は、量の符号と区別しにくい。読むかは Q1-4 |
| Yーの方向に10mm（長音「ー」） | 聞き返し（知らない言葉） | 「ー」は方向語ではない（マイナスと推測しない） |
| Y正の方向・Y負の方向 | 聞き返し | 初期の方向語ではない |
| Yマイナス側に／Y-の向きに／Y-の方へ | 聞き返し | 「側」「向き」「方」は初期の対象外（Q1-2） |
| Y--方向に／Y+-の方向に | 聞き返し | 符号が2つ |
| Y-の方向にマイナス10mm／Y-の方向に+10mm | 聞き返し（向きの指定が2つ） | 同じ向きでも、逆の向きでも、どちらか1つを選ばない |

### 2-3. 案1-a でも必ず残すもの（今の止め方・聞き返しの順番）
新しい形で軸と符号が読めても、`_pre_check_core` の順番は変えない。先に止まるものは今どおり先に止まる：
打ち消し → 繰り返し → 承認・起動・前後の言葉 → 操作が無い → 操作が2つ → 位置の形 → 位置が2つ → 知らない言葉（B1） → 場所の言葉 → はぐれた符号 → 変更が2つ → 右・左 → 上下と軸の2つの読み方 → 上下の向きが未確認 → 量 → 軸が無い・2つ → 符号が無い → 向きが2つ。
そのあと今どおり Claude（またはモック）の `propose_position` → `check_proposal`（`axis_source_gate` を含む）→ `jbi.plan_shift` の検査 → 確認表示 → 承認ボタン。

追加で、**条件の言葉**を打ち消しと同じ扱いで先に止める（今は知らない言葉として聞き返しになっているだけ。つなぎの言葉の一覧を将来広げても通らないように、明示的に止める）：

```
CONDITION_WORDS = ("もし", "ならば", "なら", "たら", "だったら", "れば", "なければ", "場合", "としたら", "とすれば")
CONDITION_MESSAGE = "{word}などの条件の言葉があるため、変更しません。してほしいことだけを言ってください"
```
（止めるか聞き返すかは Q1-5。この設計は止める側）

### 2-4. 案1-b：Claude の補助（プログラムで読めなかったときだけ）

#### 補助を呼ぶ条件（すべてを満たすときだけ。1つでも外れたら今の聞き返し・止めるのまま）
1. 設定で補助を入れている（既定は入れない）。本物の Claude かモックか（`claude_interpreter.from_env`）は今と同じ
2. 案1-a まで含めた `pre_check` の結果が「聞き返し」で、その理由が**知らない言葉（B1）だけ**、または**はぐれた符号だけ**
3. 操作は移動（`op == "move"`）だけ。速度・選択・比較・元に戻すは呼ばない
4. 打ち消し・元に戻す言葉の打ち消し・条件の言葉・繰り返し・疑問の形・「〜します」「〜ます」の言い終わり・場所の言葉・承認や起動の言葉・前後の言葉・右左の言葉・上下の言葉（上げ・下げ・上に・下に）・座標の値の言葉（Y座標・Yの値）が無い
5. 量のはっきりしない言葉（漢数字・少し・半分・単位の違う数・区切りのある数字・細かすぎる小数）が無い
6. 文全体で、軸の文字がちょうど1つ、符号の言葉がちょうど1つ以下、数字＋mm（ミリ）がちょうど1つ、位置番号が1つ以下
7. 知らない言葉が、止める語の一覧（下の `ASSIST_STOP_WORDS`）に1つも当たらず、合わせて3つ以下・それぞれ4字以下
8. 承認待ちの候補が無い・位置が決まっている（今の `flow._instruction` の「Claude に送らない」条件と同じ）
9. この発話で、まだ補助を呼んでいない（1つの発話で1回だけ。やり直さない）

```
ASSIST_STOP_WORDS = 打ち消し（NEGATION_WORDS）・条件（CONDITION_WORDS）に加えて
  "以外", "逆", "反対", "戻", "前回", "同じ", "倍", "半", "追加", "合計", "まで", "から", "以上", "以下", "未満", "超",
  "ずつ", "毎", "回", "約", "くらい", "ぐらい", "ほど", "程度", "たぶん", "多分", "かも", "かな", "例えば", "また", "さらに", "も"
```
（一覧は網羅できない。当たらなくても、最後は人の確認と今の検査で止める。残存リスク参照）

#### Claude に送るもの・返させるもの
- プログラムが発話を**言葉の列（トークン）**に分け、番号と種類を付けて送る。種類はプログラムが決める：
  `AXIS`（X・Y・Z の1字）・`SIGN`（+・-・プラス・マイナス）・`NUMBER`（数字）・`UNIT`（MM・ミリ）・`POSITION`（C と5桁）・`DIR`（方向・軸方向・軸）・`PARTICLE`（の・に・へ・を）・`SEP`（、。,・そして・それから・か・と・や）・`OTHER`（それ以外）
- 道具は2つ（strict、`tool_choice` は auto。今の `propose_position` と同じ約束）：
  - `read_direction`：`{"axis_token": 整数, "sign_token": 整数 または null, "number_token": 整数, "unit_token": 整数, "filler_tokens": [整数, …]}`。**番号だけ**で、文字・数・軸の名前は返させない
  - `ask_user`：`{"question": 文字}`（Claude の文は使わない。決まった文にする）
- 送るのは、発話の言葉の列・選んでいる位置番号・位置番号の一覧だけ（今の `build_request` と同じ範囲。ジョブの中身・座標値は送らない）

#### プログラムの照合（1つでも通らなければ補助の答えを使わず、今の聞き返しの文を返す。候補は作らない）
- V1（形）：道具の名前が2つのどちらか、`tool_use` がちょうど1件、項目がちょうどこの5つ、どれも整数（bool でない）か null、番号が列の中にある
- V2（種類）：`axis_token` の種類が AXIS、`sign_token` が SIGN（null のときは文に SIGN が1つも無いこと）、`number_token` が NUMBER、`unit_token` が UNIT で `number_token` のすぐ後（空白だけ挟んでよい）、`filler_tokens` はすべて OTHER
- V3（全部を使う）：文の中の AXIS・SIGN・NUMBER・UNIT・OTHER のトークンが、返った番号でちょうど全部（使われない軸・符号・数・知らない言葉が残らない）
- V4（**同じ命令に属するか**）：
  1. 選んだ AXIS・SIGN・NUMBER・UNIT の番号の最小〜最大の間に `SEP` が無い（1つの節の中）
  2. 符号の付き方がどちらか1つに決まる：
     (a) 軸に付く：AXIS と SIGN の間が `DIR(軸)`・`PARTICLE(の)`・空白だけで、SIGN のすぐ後が `PARTICLE(の)`・`DIR`・空白・`PARTICLE(に・へ)` のどれか
     (b) 量に付く：SIGN のすぐ後（空白は可）が NUMBER
     (a) にも (b) にも当たらない、または両方に当たる → 使わない
  3. 軸のまとまり（AXIS〜DIR）と量（NUMBER＋UNIT）の間にあってよいのは、`PARTICLE`・空白・`filler_tokens` だけ。`filler_tokens` は2つまで
  4. 位置番号があるなら、軸のまとまりより前にある（「C00003をY-の方向にさ10mm」）。後ろにある形は使わない
  5. 文の中に、選んだもののほかの AXIS・SIGN・NUMBER・POSITION が無い（V3 と同じ。複数の候補があれば、そもそも補助を呼ばない：条件6）
- V5（**数・単位・小数点・符号を変えない**）：量は `number_token` の元の字をそのまま `Decimal` で読む（float に通して書き直さない。小数点以下6けたまで、今の `MAX_AMOUNT_DECIMALS`）。符号は `sign_token` の字（+・プラス → +1、-・マイナス → −1）。軸は `axis_token` の字
- V6（**元の文に無い情報を補っていない**）：`sign_token` が null なら符号は決まらない → 今の「プラスですか、マイナスですか？」を返す（＋を補わない）。位置は発話の位置番号か、選んでいる位置だけ（Claude からは受け取らない）
- V7（読み直し）：上から作った決まった文（例「C00003をYのマイナス10ミリ」。今の `dialog.canonical_text` と同じ形）を `read_utterance` → `pre_check` に通し、`ok` で、読んだ軸・符号つきの量が V5 の値と完全に一致する。違えば使わない
- V8：補助の答えと照合の結果を作業ログに残す（「Claude の補助：番号 2・3・6・7。照合に通りました」）。Claude の文は残さない・出さない

#### 確認の聞き返し（数はプログラムが入れる。候補はまだ作らない）
```
ASSIST_CONFIRM = ("「{heard}」を、{pos}を{axis}の{sign_word}{amount}ミリ動かす指示として読みました"
                  "（読み方を Claude が補助しました）。この内容で変更の候補を作りますか？"
                  "（承認は、このあとの確認表示のボタンで行います）")
```
- `{heard}` は聞こえた文、`{pos}`・`{axis}`・`{sign_word}`（プラス／マイナス）・`{amount}` は V5 の値。Claude の文は使わない。`fill_blanks` と同じく、空欄のほかに数字・断定語があれば固定の文にする
- ボタンは2つ：［この内容で候補を作る］（決まった文を、選んでいる位置を入れて（`pin_choices`）ふつうの指示として送る）／［言い直す］（何もしない）
- 声・文字の「はい」「OK」では進めない（今どおり `_APPROVE` で止める）
- ［この内容で候補を作る］を押した後も、ふつうの指示と同じ道：`Session.hear` → `pre_check` → Claude（モック）の `propose_position` → `check_proposal`（`axis_source_gate`）→ `plan_shift`（20mm・累積・MOVL・PL・共用…）→ 候補 → 確認表示 → 承認ボタン → 出力ボタン。**どれも省かない**
- 選択肢は古くなったら使わない：位置を選び直した・新しい指示があった・候補ができた後に押されたら、今の仕組み（選択肢の文に位置番号を入れる・新しい指示で前の聞き返しを捨てる）で、別の位置に当てない

#### 補助が失敗・断ったとき
- `ask_user`・通信の失敗・refusal・形の違う答え → 補助は使わず、今の「…が分かりませんでした。軸（X・Y・Z）と向きと量を、もう一度言ってください」を返す。モックへ自動で切り替えない（今の `InterpreterError` の決まり）

### 2-5. 止める・聞き返す場合の一覧（案1）
| 場合 | 結果 |
|---|---|
| 打ち消し（動かさないで・駄目・いや・じゃなくて） | 止める（今どおり、いちばん先） |
| 条件（もし・なら・たら・れば・場合） | 止める（新しく明示） |
| 疑問の形（？・ですか）／「〜します」「〜ます」 | 今どおりの確かめ（候補にしない） |
| 軸・量・位置・符号が2つ以上／変更が2つ | 聞き返し（今どおり） |
| 符号なし | 聞き返し（プラスかマイナスか） |

## 3. 案2：右・左・手前・奥（・前・後ろ）の方向

### 3-1. 方針（チャッピーの見直しの条件）
- 「ロボットの正面に立つ人」を一律の基準にしない。**設備ごとに、操作方向の基準（どこに立って見た向きか）と座標系を、専門家が登録する**
- 登録があり、照合に通ったときだけ使う。登録が無ければ6択（推測しない）
- 座標系が分からない・対応が曖昧なら、6択も出さずに止める
- 登録は CLI で人が内容を見て入力したときだけ書く（今の `updown.py register` を広げる）。音声・Claude・画面のボタン・API からは書かない

### 3-2. 登録の形（項目案。`updown.py` の設定の version 2）
今の `records/updown.json`（schema `voice-teaching/updown`、version 1、上下だけ）はそのまま読める。version 2 を足し、同じ検査（知らない項目・重複項目・空の根拠・NaN・bool の取り違え・時差の無い日時・未来の日時 → 読まない）を通す。

```json
{
  "schema": "voice-teaching/updown",
  "version": 2,
  "cell": "（設備の名前。唐川さんが決める：Q2-1）",
  "robot": "HC20DT",
  "coordinate": {"postype": "ROBOT", "rectan": true, "user": null, "tool": 0, "frame": null, "rj": false},
  "reference": {
    "description": "（基準の立ち位置と見る向き。人が書く。例の書き方は Q2-2）",
    "evidence": "（基準をどう決めたか）"
  },
  "directions": {
    "上": "Z+", "下": "Z-",
    "右": "Y-", "左": "Y+",
    "手前": "X-", "奥": "X+"
  },
  "pair_evidence": {
    "上下": "（ペンダントでロボット座標の Z+ にジョグして、真上へ動いた、など）",
    "右左": "（基準の位置から見て、ロボット座標の Y- にジョグしたら右へ動いた、など）",
    "手前奥": "（同じ）"
  },
  "confirmed_by": "（確認した人）",
  "confirmed_at": "2026-11-05T10:00:00+09:00",
  "fingerprint": "（中身の sha256。今と同じ計算）"
}
```
（右＝Y− などの値は形の例で、どの向きかを決めたものではない）

形の検査（1つでも外れたら、ファイル全体を読まない＝未確認）：
- `directions` の言葉は 上・下・右・左・手前・奥 のうちの組だけ（上下・右左・手前奥）。**組の片方だけは不可**。前・後ろは今は登録できない（Q2-3）
- 値は `X+`・`X-`・`Y+`・`Y-`・`Z+`・`Z-` のどれか。組の2つは同じ軸で逆の符号
- 組どうしは違う軸（右左と手前奥が同じ軸、などは不可）。上下は今どおり `Z+`／`Z-` だけ（逆向きの設置は決まってから）
- 組ごとに `pair_evidence` が空でない。`reference.description`・`reference.evidence` が空でない
- `cell`・`robot`・`confirmed_by` は空でない短い文字。`coordinate` は今の version 1 と同じ検査（ROBOT・RECTAN・USER なし・ツール番号は0以上の整数・FRAME と RJ の組）
- 斜め（ロボットが設置で回っていて、右がどの軸とも一致しない）は登録できない（Q2-5）

CLI（今の `register` を広げる）：
- `python -m voice_teaching.updown register --job … --cell … --robot … --by … --reference … --pair 右左=Y-,Y+ --pair-evidence 右左="…"`
- 内容を表示し、**組ごとに対応を打ち直してもらう**（例「右=Y-」と入力。表示と違えば書かない）、最後に yes。EOF・中断・yes 以外 → 書かない。既にあるファイルは `--overwrite` が無ければ置き換えない（今どおり）
- 書く前に、読む側と同じ検査を通す（今どおり）

### 3-3. 照合の条件（毎回の指示・承認・出力・状態の表示のときに読み直す。今の上下と同じ）
1. 設定ファイルがあり、形が正しい（上の検査）
2. 指紋が中身と合う（合わなければ「変更済み」）
3. アプリの起動オプション `--cell`（新しく足す。既定なし）が設定の `cell` と同じ。`--cell` が無ければ、右左手前奥は使わない（登録なしと同じ扱い。上下は今どおり version 1 と同じ照合）
4. アプリの `--robot` が設定の `robot` と同じ
5. ジョブの座標系（今の `job_coordinate`）が設定の `coordinate` と同じ。ジョブの座標系が読めない（`///USER`・PULSE・ツール番号が2つ以上・FRAME が決めた形でない・読めない所）なら不一致
6. 発話の言葉が `directions` に登録されている（登録に無い言葉は、登録から作らない。右左から手前奥を作らない）
7. 候補を作ったときの照合の結果（token：状態・指紋・ファイルの sha256）と、承認・出力のときが同じ（違えば承認できない・承認を取り消す。今の `UPDOWN_CHANGED_*` と同じ）

### 3-4. 画面の流れ

#### 登録あり・照合に通ったとき（例：C00003 を選んで「右に10mm」）
1. プログラムが「右」を登録の対応（例 Y−）に変える。読み取りの事実に「どこから来た軸か」を残す（`relative_axes` のような新しい項目。上下の `vertical` と同じ考え方）
2. `axis_source_gate` は、登録から来た軸を「登録の照合に通ったときだけ」通す（今の上下の Z と同じ）
3. 確認の1タップ（初期案。外すかは Q2-6）：「「右」は、この設備の登録で Y− です（基準：{reference.description}、{confirmed_by} さんが確認）。C00003 を Y− に 10mm 動かす候補を作りますか？」［この内容で候補を作る］［言い直す］。数・軸・名前はプログラムが入れる
4. ふつうの検査（20mm・累積・MOVL…）→ 候補 → 確認表示。確認表示に「「右」＝ Y−（登録：{cell}・{confirmed_by} さん・{confirmed_at}）」の1行を必ず出す → 承認ボタン
5. 承認の記録と作業ログに、使った登録の指紋と確認した人を残す（今の上下と同じ）

#### 登録なし（ファイルが無い・`--cell` が無い・その言葉が登録に無い）
- 「「右」が X・Y・Z のどれに当たるかは、この設備では登録されていません（推測しません）。動かす向きをボタンで選んでください」と、6択を出す（下の表示）
- 6択を出すのは、位置が1つに決まり、量が1つ（mm、0 でない、上限以下）で、向きの言葉が1つだけのとき。それ以外は6択を出さず、今どおり聞き返す・止める
- ボタンを押すと、決まった文（「C00003をYのマイナス10ミリ」。位置番号を入れる）をふつうの指示として送る。そのあとの検査・確認表示・承認ボタンは省かない

#### 登録はあるが照合に通らない（不一致・変更済み）
- 6択も出さずに止める。理由（ツール番号が違う・設備の名前が違う・設定が変わった など）を出し、「X・Y・Z と向き（Yのマイナス など）で言ってください」と案内する

### 3-5. 6択の表示内容（登録なしのとき）
3D の矢印だけにしない。次の4つを文字で出す（値はすべてプログラムがジョブから計算する。Claude は呼ばない）：

## 7. 残存リスク（正直に）

- **音声認識の符号の聞き違いは止められない**：「Yマイナスの方向」が「Yプラスの方向」と返れば、案1-a ではそのまま Y +10 の候補になる。最後の止めは、入力欄・確認表示で人が見ること。読める形を増やした分、この経路も増える
- **符号が落ちる形**（「Xマイナス方向に5ミリ」→「X 方向に 5mm」、CHECKER_022 P1-a）は今どおり聞き返しになるが、全部の落ち方を試したわけではない
- **正規表現を広げると、ほかの言い方の読み方が変わるおそれ**：今のテスト（家のPCで 4987 件）と A1 の回帰で見るが、全部の言い方は網羅できない
- **Claude の補助**：番号・種類・同じ節・符号の付き方はプログラムで照合できるが、「知らない言葉（さ・ね など）が意味を変えないか」は、Claude の判断と人の確認に頼る。止める語の一覧は網羅できない。補助の効き目は小さい（照合が厳しいため、補助で読めるのはつなぎの言葉が混ざった形だけ）
- **案2 の登録は記録で、本人の証明ではない**（今の上下の設定と同じ。JSON を書ける人は設定も書ける）。登録した人の向きの判断が誤っていれば、「右」は誤った軸になる
- **作業者が基準の位置に立っていないとき**、「右」の意味がずれる。アプリは作業者がどこに立っているかを知らない
- **6択で人が向きを選び誤る**：推測するのは人になる。表示に変更後の値を出すが、物理的な位置関係を保証するものではない
- **案4 はサーバーのメモリの状態を消すだけ**：古い応答・別のタブの扱いはテストで見るが、全部の順番は網羅できない。作業ログはメモリだけなので、戻ると消える
- **0章の発見（別のジョブを読み込んでも古い番号で承認できる）は、今のコードに残っている**。画面からは古い番号を使わないが、サーバー側の保証は無い
- 検査を通ったことは、物理的な安全の保証ではない。変更後の経路は人が確かめてから承認する
