## 0. 結論（1分で読む版）

1. **今の撮影版では、変更の指示を Claude が理解する場面がほとんど無い。** Python の正規表現が「位置・軸・向き・量」を全部読めたときだけ Claude を呼び、しかも **Claude の答えが正規表現の読みと1文字でも違えば捨てる**（★ `utterance.py:1802-1842` `check_proposal`）。つまり Claude は「同じ答えを言うか、失敗するか」しかできない。理解力の上限は正規表現で決まっている。
2. 利用者が見る「分かりませんでした」の**ほとんどは Python が Claude に送る前に出している**（2章の表）。Claude 自身が理解できなかった例は、調べた範囲ではわずか。
3. 直し方の芯：**Claude が意味を読み（意図・対象・方向・量・文脈・聞き返し）、Python は Claude の読みを「決まった指示の文」に組み立て直して、今の安全の流れ（pre_check → check_proposal → jbi の判定 → 差分 → 画面の承認 → SIM 出力）にそのまま通す。** 安全の判定は1つも Claude に移さない。
4. 量があいまい（「もう少し」）なときは **Claude にも Python にも数を決めさせない**。「何ミリですか？」と聞き、答えの「5ミリ」を前の話と合わせる。右・左が軸のどちらか未確定なら、勝手に決めずに確かめる（今のボタン）。
5. **提出（11/8 14時）前に入れる価値があるのは「小さく安全な部分」（9章の段階1）まで**。Claude を先に立てる作り替え（段階2）は、実 API の合格基準を 11/7 夕方までに満たしたときだけ、切り替えスイッチ付きで。満たさなければ提出後に回す。撮影の動画は 60f3d24 で撮っているので、提出物の動きと動画が食い違わないことも条件にする。**→ 11/6 夜の決定（0-1 章）：段階0・1 は独立ブランチでの準備・検証だけで統合は保留、段階2 は提出後が原則。**

## 4. 改善の設計

### 4-1. 役割の分け方

```
 声 → 文字（ブラウザ・今のまま。自動では送らない）
   → [Python] 入口の守り（今のまま・Claude より先）
        承認・出力・実行の言葉 → ボタンへ案内（声の承認は禁止のまま）
        候補・承認があるときの言い直し・ためらい → Spec A の取り消し・保留（安全側。Claude の答えで緩めない）
   → [Claude] 理解（新）：構造化出力で「読み」を返す。数の計算・安全の判定はしない
   → [Python] 読みの検査（新）：根拠の文字列が本当に発話にあるか・数が根拠と一致するか・位置が一覧にあるか
   → [Python] 会話の枠（新）：足りない項目を持って、聞き返す／前の続きを合わせる
   → [Python] 決まった指示の文に組み立てる（例「C00003をYのプラス5ミリ」）  ← dialog.py と同じやり方
   → [Python] 今の流れ：pre_check → 上下・向きの確認 → Claude A（今の確認）→ check_proposal → jbi の判定（20mm・累積・共用・座標系・構造）→ 差分 → 画面のボタンで承認 → 合成 JOB だけ SIM 出力
```

要点：
- **Claude の読みは、最後は今と同じ「決まった指示の文」になって、今の安全の流れを全部通る。** 安全の判定・承認・出力のコードは変えない。
- 正規表現は「入口の守り」（承認の言葉・取り消し・ためらい・否定）と「組み立てた文の検査」に残す。「理解」の役目からは外す。
- Claude が「分からない・足りない」と言えば、Python は**その項目だけ**を聞く（Thomason ら IJCAI-15 の、項目ごとに確かめて足りない所だけ聞く方針と同じ）。

### 4-2. Claude の新しい呼び出し「理解」（`understand`）

- **構造化出力**：`messages.create(..., output_config={"format": {"type": "json_schema", "schema": …}, "effort": "medium"})`。SDK 2.3.0 にある。claude-sonnet-5-5 は対応モデルの一覧にある（公式資料）。
  - strict の道具では、このモデルは `tool_choice` を `any`/`tool` にすると 400（公式資料）。今のコードも `auto` で、文字だけで返されると FAILED になる。**構造化出力なら必ず JSON が返る**ので、こちらを選ぶ。
  - 形が正しいことは保証されるが、**値が正しいことは保証されない**（公式資料）。そのため 4-3 の検査が要る。
- **thinking**：既定の adaptive のまま。system の最後に「答える前によく考えてください」を足す（Sonnet 5.5 の資料。構造化出力では thinking の中でしか考えられないため）。JSON に「理由」の欄は作らない（拒否の原因になると資料にある）。短い `note` だけにする。
- **文脈（Context Engineering）**：
  - 毎回、Python が作る `<state>` を渡す：位置の一覧・選んでいる位置・聞いている途中の項目（4-4）・直前の操作（位置・軸・向き・量）・候補の有無と承認の状態・上下の向きの確認済みかどうか・右左の対応の確認済みかどうか。
  - 生の会話は直近の数往復だけ。
  - 状態は Python が持ち、Claude には覚えさせない。
  - system・例・スキーマは毎回同じ文字列にして、プロンプトのキャッシュに載せる。変わる `<state>` は最後に置く。
- **few-shot**：`<examples>` に 5つ。①ふつうの指示 ②「もう少し右」→ 量を聞く ③続きの「5ミリ」 ④言い直し「いや3ミリ」 ⑤関係ない話。規則を並べるより、代表の例を少し見せる（Context Engineering の記事）。
- **スキーマ（案）**：全部の項目を必須にし、決まらないものは `null`。

```json
{
  "intent": "move | select | undo | compare | repeat_count | question | approve_or_export | cancel | chit_chat | unclear",
  "status": "ready | need_clarification | out_of_scope",
  "target": {"ref": "explicit | selected | previous | none", "position": "<一覧の enum> | null", "evidence": "発話の中の文字列 | null"},
  "direction": {"word": "X+|X-|Y+|Y-|Z+|Z-|上|下|右|左|前|奥 | null", "evidence": "… | null"},
  "amount": {"kind": "stated | same_as_previous | vague | none", "value": "number | null", "unit": "mm | cm | null", "evidence": "… | null"},
  "is_correction": "boolean",
  "missing": ["target | direction | amount"],
  "question": "聞き返しの文 | null",
  "note": "短い説明（画面には出さない）"
}
```

- **「少し」は数にしない**：`amount.kind = "vague"` なら必ず `status = need_clarification`、`missing = ["amount"]`。既定の量（例：5mm）を決める案は、勝手な量の候補になるので採らない。
- `same_as_previous`（「さっきと同じだけ」）は、Python が直前の操作の記録から量を取る。記録が無ければ聞く。
- **言い直しは承認を戻さない**：`is_correction` は Python の Spec A をもっと安全側（保留・取り消し）にだけ使い、保留を外す向きには使わない。

### 4-3. Python による読みの検査（Claude を信じすぎない）

正規表現との完全一致（R2）をやめ、次の決まった検査にする。

1. `evidence` は、発話の文字列に（全角・半角を揃えたうえで）**そのまま含まれること**。含まれなければ、その項目は無かったことにして聞き返す。
2. 量は `evidence` から **Python が数を読み直し**（漢数字・「十ミリ」・「1センチ」も Python の換算）、Claude の `value`・`unit` と一致したときだけ使う。一致しなければ聞き返す。**mm への換算は Python だけ**が行う。
3. 位置は一覧の enum。`ref = selected` は、選んでいる位置があるときだけ。`ref = previous` は、直前の操作の記録があるときだけ。
4. 方向：
   - X±/Y±/Z± はそのまま使う。
   - 上・下は、上下の向きが確認済みのときだけ Z± にする。未確定なら今の確認の文を出す。
   - 右・左・前・奥は、**右左の対応の確認（今のボタン）が済んでいるときだけ**軸にする。未確定なら確認を出す。そのとき、ほかの項目（量・位置）は会話の枠に残す（R10 を直す）。
5. `intent` が `approve_or_export` なら、ボタンへの案内だけ（声の承認は禁止のまま）。`cancel` は Spec A の取り消し。
6. ここを通ったら、決まった指示の文を作って今の流れへ。**今の `check_proposal` と jbi の判定は1つも外さない**。組み立てた文を `pre_check` が読めるので、完全一致の確かめも自然に通る。

### 4-4. 会話の枠（Python・新）

- 中身：`intent`・`target`・`axis/direction`・`amount_mm`・`missing`・作った時刻・何往復目か・候補の世代（`cand_gen`）。
- 1つの JOB の画面の中だけ。保存しない（今の決まり v2.1 の19 と同じ）。
- 次のときに消す：位置を選び直した（ただし `target` だけを入れ替え、量は「C00004 にも同じ？」と確かめる）、JOB を読み直した、取り消しの言葉、3往復しても埋まらない、候補ができた。
- 「もう少し右に寄せて」（C00003 を選択・右左は確認済み）→ 枠 `{move, C00003, Y+, amount: missing}` →「何ミリですか？」→「5ミリ」→ 枠が埋まる →「C00003 を Yプラス（右）に 5mm ですね」の候補 → 差分 → 画面のボタンで承認。
- 右左が未確定なら：→「右は Yプラス で合っていますか？［合っている］［違う］」→ ボタン → 枠の残りの量を聞く。確認の答えで枠を作り直す（R10）。

### 4-8. 「だめ」「ノー」「大丈夫？」（D3・確定した最低限）

### 4-9. 右・左の対応を覚える条件（D5）

  2. 対象の位置
  3. 方向の対応（例：右 = Yプラス）を、人が画面のボタンで確かめた
- 覚えたものは、**その会話（その JOB の画面）の中だけ**。保存しない。

### 7-3. モックと実 API を分ける

- **モック（毎回・CI）**：Claude の JSON を固定の台本で返す。見るのは Python の検査・会話の枠・安全の流れだけ。「Claude がでたらめを返したとき」（量が根拠と違う・一覧に無い位置・vague なのに数がある・右左が未確定なのに軸）も台本で入れる。期待は「候補なし」。
- **実 API（手で動かす）**：`tools/nl_eval/run_live.py`。同じ 100件を 2回流し、結果は `output/nl-eval/live-<SHA>-<n>/`。モックの結果とは別のフォルダ・別の表。表には必ずモデル名・SHA・日時・件数・費用を書く。
- 費用の見込み：1件あたり 入力 約3千トークン（キャッシュが効けば大半は読み出し）・出力 約0.5千トークン（thinking を含む）。100件×2回＋調整の分で、数ドル程度の見込み。
- **D2：今夜は実 API の評価をしない・費用を使わない**。実 API の評価は、提出後か唐川さんの指示のあと。それまではモックの評価と、クロークの記録済みの結果（243件・focus-47）との照合だけ。

## 付録：調べた資料

- 構造化出力 https://platform.claude.com/docs/en/build-with-claude/structured-outputs ：全部のモデル・ベータのヘッダーは不要。数の範囲（minimum/maximum）は使えない。初回はスキーマのコンパイルで遅く、24時間キャッシュ。形は保証、値は保証しない。
- 道具の使い方 https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview と strict の道具：情報が足りないとき「Sonnet は聞くこともあるが、それらしい値を推測することもある」とある。→ null と聞き返しの道を必ず作る理由。Opus 5.5・Sonnet 5.5 では `tool_choice` の `any`/`tool` は 400。
- Context Engineering https://www.anthropic.com/research/effective-context-engineering-for-ai-agents ：少なくて効く情報を渡す・代表の例を少し・状態は外に持つ。
- arXiv 2401.11838（Nwankwo & Rueckert 2024 "The Conversation is the Command"）：LLM が決まった動作の中から選び、実行は決まったコードが行う。**この作りの先例にはなる**が、聞き返し・会話の続き・「右」を座標に結ぶ方法は扱っていない。関係は弱〜中。
- IJCAI-15 273（Thomason, Zhang, Mooney, Stone "Learning to Interpret Natural Language Commands through Human-Robot Dialog"）：項目ごとの確からしさを持ち、足りない項目だけを聞き返し、確かめてから動く。**聞き返しの設計に直接役立つ**。LLM 以前の研究で、座標の話ではない。
- 方向の言葉を座標に結ぶのは、どちらの論文も扱っていない。→ Python の決まった表と、人の確認で行う。
